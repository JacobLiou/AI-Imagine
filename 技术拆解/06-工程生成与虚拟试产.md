# 工程生成与虚拟试产

对应 [AI 成功案例](../AI%20成功案例.md) 的路径六。公开样板有两截，不要合成一个产品：

- **虚拟试产**：西门子 Digital Twin Composer 加 NVIDIA Omniverse。百事在美国工厂和仓库的初期部署报告产能 +20%、资本开支少 10–15%，物理改造前识别最多 90% 的问题。西门子另述佳得乐产线在三个月内达到该产能提升。Digital Twin Composer 在 2026 年 CES 仍是早期客户阶段。
- **工程生成**：NI Nigel 在 TestStand 里按规格书生成测试序列，在 LabVIEW 里按提示生成与已连接硬件相关的测量程序。2026 年 7 月 28 日新闻稿给出的是内部基准：代表流程的开发和部署工作量最多减少 50%。生成结果仍由工程师确认。西门子 Eigen 打算在 TIA Portal 里做完一段自动化工程，公开材料还没有量化收益。

两截共用一个决策：生成物要能在发布前被执行一遍。虚拟工厂里执行的是物流和节拍，测试和 PLC 里执行的是编译和仿真。

## 技术决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 生成目标 | 已有语言的第一版：结构化文本、测试序列、布局方案 | 有语法和运行时可以判错。自由散文没法验收 |
| 验收 | 编译、强制输入、跟踪变量；或在孪生里跑节拍和干涉 | SemaPLC 把「写完 ST → 编译 → 跑 OpenPLC → 对输入 → 看变量」做成工具，而不是只看代码像不像 |
| 发布 | 人确认后才进安全联锁或真线改造 | 成功案例里的 Nigel、百事都停在确认之前 |
| 工厂模型 | 资产壳（AAS）描述设备信息和接口；实时状态另走物联网孪生 | 说明书式孪生和秒级状态不是同一个数据库 |
| 物理仿真 | 布局、物流、节拍用离散事件或物理引擎；控制逻辑用 PLC 运行时 | 一个 3D 场景替代不了控制闭包 |

百事那类系统还依赖计算机视觉把真实路径吃进孪生。那是几何和物流孪生，不是控制代码生成。

## 架构

工程生成一条线：

```text
规格、现有程序、硬件清单
    → 模型起草 IEC 61131-3 ST 或测试序列
    → 语法检查
    → 编译（matiec / 厂商编译器）
    → 运行时（OpenPLC 或仿真器）
    → 强制输入、跟踪输出、对照验收场景
    → 差异展示给工程师
    → 确认后导出，仍由现有变更流程下装
```

美的开源的 SemaPLC 把后半段做成智能体可调用的工具：`plc_check`、`plc_compile`、`plc_buildAndRun`、`plc_readVariables`、`plc_forceVariables`、`plc_trace`，运行时是 OpenPLC Runtime 加 matiec，用 Docker 起。场景仿真用实时变量驱动传送带、水箱、电机的示意图。这是「生成必须落到可执行工具」的参考实现，不是西门子或 NI 的产品架构。

虚拟试产一条线：

```text
资产主数据 + 布局 + 节拍与路径
    → 可运行的工厂模型（离散事件，或带物理的三维场景）
    → 改一个参数：缓存、人员、设备数、路线
    → 看吞吐、堵塞、干涉、在制品
    → 方案比较
    → 人决定是否资本开支
```

资产的数字身份用管理壳。IDTA 的 Asset Administration Shell 分元模型、API 和数据规范。Eclipse 侧的开源栈是：AASX Package Explorer 编辑壳，BaSyx 提供壳和子模型的服务，Eclipse Ditto 保存设备的当前状态。Ditto 可以用出站映射，把 Thing 的变化写成 AAS 子模型元素，推给 BaSyx。这样「设备现在是什么状态」和「设备的出厂信息、接口」分开存。

## 经典技术

- **IEC 61131-3**：PLC 的结构化文本、梯形图等。生成 ST 是因为它能文本化、能 diff、能编译。matiec 把 ST 译成 C。
- **编译器当验收器**：词法、语法、符号表、类型检查。生成模型不替代这几遍。
- **软件在环**：控制程序在 PC 或容器里跑，工厂用简化模型闭环。真机在环是后一阶段。
- **管理壳 AAS**：一个资产一个壳，子模型描述铭牌、文档、技术数据。它是工业数字孪生的互操作模型，不是渲染引擎。
- **离散事件仿真**：队列、资源、节拍。适合在三维场景之前回答「产能和缓存够不够」。
- **物理级三维孪生**：NVIDIA Omniverse 是百事案例里的可视化与仿真库。开源侧没有一个对等的「整厂 Omniverse」。布局研究可以先离散事件，确认要看干涉和人机路径时再上三维。

## 参考范式

1. 规格或现有工程资产进，草稿出，工具链验收，人下发。
2. 验收场景事先写好：哪些输入必须产生哪些输出，哪些状态禁止出现。
3. 孪生先回答一个改造问题（产能、缓存、路线），不要先追求全厂可视。
4. 实时状态（Ditto 一类）和生命周期资料（AAS）通过明确映射同步，不把原始点表直接当孪生。

Nigel 的产品边界和这个范式一致：2026 Q3 能按规格书生成序列或占位模块，工程师改完才成为测试。更早的 SIVA 框架用 LabVIEW 加 TestStand 复用把后硅验证效率提高至少 30%，那是软件框架，不是生成模型。两件事可以叠在一起：框架规定序列长什么样，模型只填框架里的空。

| 仓库 | 拿它看什么 |

| [Eclipse Ditto](https://eclipse.dev/ditto/) | 设备状态孪生；[与 BaSyx 的映射说明](https://eclipse.dev/ditto/2024-02-27-integrating-ditto-aas-basyx.html) |

许可证以各仓库为准。OpenPLC / matiec 的许可证和 SemaPLC 不一定相同，商用前分别看。

百事与西门子、NVIDIA 的数字没有开源复现。能复现的是「方案在模型里跑过再花资本开支」这个决策顺序，用离散事件仿真或 AAS 加状态孪生做一个工段即可。

## 不要照搬的地方

不要把聊天里生成的梯形图直接下装到安全 PLC。不要把 Omniverse 场景当成已经验证的控制逻辑。Eigen 还没有公开收益数字，不能当作选型依据。第一期只生成一种资产：要么测试序列，要么一个工段的 ST，并且每份生成物都有失败测试。
