# 制造知识助手

对应 [AI 成功案例](../AI%20成功案例.md) 的路径五：维修、8D、SOP、失效案例先变成可检索的组织记忆。西门子维护 Copilot 也属于这一层，但它接在 Senseye 的案例和证据上，不是一个空的聊天窗口。

制造业里这篇和通用 RAG 教程的差别是：答错会进现场动作。所以架构的中心是引用、版本和拒绝，不是把文档全部塞进上下文。

## 技术决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 第一期形态 | 检索加生成，每条回答带文档号、版本、页码 | 工程师要能打开原文核对 |
| 检索 | 稠密向量加关键词（BM25），再用倒数排名融合 | 故障码、件号靠关键词；现象描述靠语义。只做一种都会漏 |
| 生成模型 | 能在单台 GPU 或本地推理服务里跑的开源模型，和检索分开评 | 机器制造商的现场研究把模型限制在约 15 GB 以内，用 Ollama 管理 |
| 元数据过滤 | 设备型号、生效日期、版本、语言先过滤再排序 | 航空维修系统里这叫有效性过滤：答案必须对这架飞机、这个日期有效 |
| 没有依据时 | 明确拒绝，不编步骤 | 地面保障设备维修管道把「文档不支持就不答」写成产品行为 |
| 代理 | 第一期不做会开单、改参数的代理 | 工具调用会把错误步骤执行掉 |

苏黎世应用科学大学在一家机器制造商的运维 RAG 研究（Procedia CIRP 139，2026，349–354）比较了纯向量、BM25 和混合检索。混合和纯向量的命中率都高于单独 BM25，最终选用混合。生成侧比较了 Gemma3 12B、Phi-4 14B、Qwen2.5 14B，用「是否符合给定上下文」和人工抽查，而不是用闲聊分数。

## 架构

```text
源文档（SOP、维修手册、8D、失效案例）
    → 解析（保留标题、表、图注、页码）
    → 按章节或按页切块，记下型号、版本、生效期、语言
    → 稠密向量 + 稀疏索引
    → 问题进来
         解析型号 / 故障码
         元数据过滤
         两路检索 → 融合 → 取少量块
    → 模型只根据这些块作答，并引用
    → 依据不足则拒绝
    → 记录问题、命中块、回答、用户是否点开原文
```

航空维修参考系统 WingFix 把这条链路再加了三条制造业一定能用到的规则：

- 内部规程优先于厂家手册。
- 非受控旧文档要标明，并要求确认。
- 件号问题可以查库存，但库存是另一个系统，不写进模型权重。

评估分成两段，不要只看最终回答好不好：

1. 检索：这道题的正确页是否出现在前 k 个块里。
2. 生成：在正确块给定时，回答是否只说了块里有的步骤。

模型再强也补不回检索没命中的那一页。

## 经典技术

- **RAG**：索引阶段嵌入文档，查询阶段取出少量表块，和问题一起送给语言模型。LlamaIndex 文档把加载、索引、检索、生成拆开，便于换向量库。
- **混合检索**：BGE 一类稠密模型和 BM25。融合用倒数排名融合（RRF）。Qdrant 的手册示例用稠密加稀疏，融合后只把极少的块送给模型。
- **分块**：按页或按标题，比固定字数窗口更能保住步骤顺序。RAGOps 在一份手册上比较过结构感知分块和滑动窗口，结构感知分出的块更多、也更贴步骤。数字会随手册变，结论是「先保留页码和标题」。
- **引用**：回答中的每个步骤能指回 `文档、版本、页`。没有指针的句子视为未接地。
- **拒绝**：检索分数低于阈值，或模型判定上下文不够时，返回「资料不足」和最接近的目录，不给操作步骤。
- **评测**：用真实工单改写成问题，黄金页由维修工程师标。LLM 当裁判只能辅助，最终抽查要领域的人看。

## 参考范式

1. 先整理一类角色的文档：维修，或工艺，或质量。不要第一期吞下全公司网盘。
2. 混合检索，强制引用，不能引用就拒绝。
3. 按型号和版本过滤。
4. 检索和生成分开打分。
5. 确认问答稳定之后，才考虑代填工单草稿。草稿仍由人提交。

西门子维护 Copilot 的产品形态是这个范式的后半段：预测维护已经产生案例和证据，助手负责把手册和案例说成维修人员能用的建议。没有前半段数据时，不要从代理做起。

## 不要照搬的地方

家电说明书演示和产线 SOP 不是同一风险。SOP 有版本和生效设备，旧版被检索到就会给出过期扭矩或过期步骤。第一期把「答错」定义成事故，把「拒绝」定义成正常结果。不要用模型去背整本手册。
