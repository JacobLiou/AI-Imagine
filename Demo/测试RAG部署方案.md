# 测试 RAG 部署方案

第一期只回答一个产品族、一段测试上的失败排查。规程走检索，数量走只读数据库。不改限值，不重测，不开工单。

验收口径见 [测试知识助手试点](../技术拆解/07-测试知识助手试点.md)。本文只写怎么部署、要什么资源、按什么顺序做。

## 部署成什么样

测试区一台推理服务器，不把规格书和测试记录送出工厂。工程师只访问内网网页。

```text
浏览器（测试班组）
    → 内网 API
         1. 识别产品族、工位、程序版本、失败码
         2. 路由器
              规程题 → 混合检索 → 生成（必须引用，否则拒绝）
              事实题 → 只读 SQL → 返回数量和口径
              改限值 / 改程序 → 直接拒绝
         3. 写入问答日志和点踩
    → 文档库（Qdrant + 原文文件）
    → 测试库只读账号（视图，不是生产库写权限）
```

模型不连接测试机。数据库账号只有 `SELECT`。

## 资源

试点按「几百份文档、一个班组、每天几十次提问」估算。文档超过五千份或要同时服务多条产线时再加机器。

| 资源 | 试点配置 | 用途 |
|------|----------|------|
| 推理服务器 1 台 | 8 核 CPU、64 GB 内存、1 张 24 GB 显卡、1 TB SSD | 嵌入、检索、14B 级模型 |
| 没有 24 GB 显卡时 | 16 GB 显卡，模型改为 7B–8B 量化 | 回答变短，50 题仍要重跑 |
| 系统软件 | Linux、Docker、NVIDIA 驱动 | 服务用容器跑 |
| 测试数据库 | 只读账号 + 一张失败汇总视图 | 事实题。不要把账号指到生产写库 |
| 人 | 测试工程师 1 名（负责人）、后端 1 名、IT 0.5 名 | 题库、管道、网络和账号 |
| 网络 | 服务器只开内网 443；测试库只允许该服务器访问 | 规格书不出厂 |

不需要 Kubernetes。一台机器上的 Docker Compose 够用。向量库和模型都放这台机器，试点不必再买三台。

软件选型：

| 组件 | 选用 | 原因 |
|------|------|------|
| 解析 | Docling；扫件质量差时用 pymupdf 按页兜底 | 保住标题、表格和页码 |
| 关键词 | BM25 | 失败码、夹具号、料号 |
| 向量 | bge-m3，中英混合 | 现象描述 |
| 向量库 | Qdrant | 能按产品族、版本、生效日期过滤 |
| 融合 | 倒数排名融合 RRF | 两路各取 20 条，融合后留 5 条 |
| 生成 | Ollama 上的 Qwen2.5-14B，或显卡不够时用 7B | 单机、可本地 |
| 日志 | PostgreSQL | 问题、命中片段、回答、点踩、归类 |
| 原文 | 服务器本地目录 | 回答里的链接打开原页 |

内部规程的检索加分高于设备商手册。两份文档冲突时，回答并列引用，不合成一句。

## 索引里每块要有的字段

切块按章节，单块不超过约 400 token，重叠只在步骤被切断时使用。每块保存：

- 产品族、测试段、工位
- 文档号、版本、生效日期、失效日期
- 页码、章节标题
- 文档类型：规格、失败代码、夹具、8D
- 是否现行。过期文档默认 `active=false`，不进检索

换版时整本旧文档标成失效，再索引新版本。不要只追加新文件、留下旧页。

## 怎么做

### 第 1–2 周：范围和题库

1. 测试负责人选定一个产品族和一段测试。
2. 写出 50 题：30 道规程、10 道事实、10 道必须拒绝。每道规程题标上文档号和页码。
3. IT 开只读账号。视图至少包含序列号、批次、工位、程序版本、失败码、测试项、测量值、上下限、复测次数、夹具号、时间。
4. 把现行规格、失败代码表、夹具说明、近两年 8D 拷到服务器的 `docs/active/`。过期文件放 `docs/archive/`，不索引。

没有这 50 题，不开始调模型。

### 第 3–4 周：索引

1. 安装 Docker、驱动、Ollama、Qdrant、PostgreSQL。
2. 解析 PDF，写入元数据和页码。解析失败的页列成清单，交给测试负责人，不静默跳过。
3. 对每块同时做 BM25 和 bge-m3 向量，写入 Qdrant。
4. 用 30 道规程题只测检索：正确页是否出现在前 5。不到 80% 就改切分和过滤，先不改生成模型。
5. 事实题对着视图写固定查询。失败码、工位、日期是参数。模型不拼接 SQL。

### 第 5–6 周：回答和拒绝

生成时把 5 个片段和问题一起送入模型。提示词规定：

- 只使用给定片段里的步骤。
- 每条步骤后面标注文档号、版本、页码。
- 片段没有该步骤时，回答「资料不足」，并列出已检索到的文档标题。
- 用户要求放宽限值、修改程序、自动重测时，不检索，直接拒绝。

然后跑完全部 50 题。应拒的 10 题必须全部拒绝。事实题的数量必须和 SQL 结果一致。

### 第 7–8 周：班组试用

内网页面四个区域：问题、回答、引用（可打开原页）、点踩原因（检索没找到 / 文档过期 / 模型说多了）。

只给一个班组账号。每天看点踩。点踩不是自动训练信号，是当天要人工归类的工单。

### 第 9–10 周：回归

补文档或调整切分后，50 题再跑一遍。规程命中不低于 80%、应拒全拒、事实题与数据库一致，才算试点通过。通过后再讨论把排障案例写回知识库；未确认的案例不索引。

## 运行时注意

- 模型、嵌入、索引版本号写在每条回答日志里。换任何一个都要重跑 50 题。
- 显卡被占满时排队，不要为了速度改成不带引用的短回答。
- 备份 Qdrant 快照、`docs/active` 和 PostgreSQL。索引可以重建，点踩日志不能丢。
- 服务器磁盘加密。测试只读账号的密码不进代码仓库。

## 试点机器上的容器

| 容器 | 作用 |
|------|------|
| `qdrant` | 向量和过滤 |
| `postgres` | 问答日志、点踩、50 题结果 |
| `ollama` | 生成模型 |
| `api` | 路由、检索、引用、拒绝 |
| `web` | 班组页面 |

嵌入模型放在 `api` 所在机器上，和文档一起留在内网。第一期不要接公有云模型。
